!> **Warning** This resource shouldn't be used with `snowflake_current_account` resource in the same configuration, as it may lead to unexpected behavior. Unless this resource is only used to manage the following parameters that are not supported by `snowflake_current_account`: ENABLE_CONSOLE_OUTPUT, ENABLE_PERSONAL_DATABASE, PREVENT_LOAD_FROM_INLINE_URL. More details in the [snowflake_current_account](./current_account) resource documentation.

-> **Note** This resource does not support all account parameters. The supported ones are listed below. This feature gap will be addressed in future releases.

~> **Note** The `ACCOUNT_PARAMETER_CATALOG_WRITE_PATH` experiment is enabled by default. The provider quotes `value` based on the parameter type, so do not wrap string values in single quotes (e.g. `value = "module_a,module_b"` for `PYTHON_PROFILER_MODULES`). Identifier values (e.g. for `NETWORK_POLICY`) are sent as quoted identifiers, so they must match the name stored in Snowflake. If you add the experiment to the [`experimental_features_disabled`](https://registry.terraform.io/providers/snowflakedb/snowflake/latest/docs#experimental_features_disabled-1) provider field, the v2.22.x legacy write path is used: some string values must be wrapped in single quotes manually (e.g. `value = "'module_a,module_b'"`), and some parameters, e.g. `DISABLE_UI_DOWNLOAD_BUTTON`, cannot be set. See the [migration guide](https://github.com/snowflakedb/terraform-provider-snowflake/blob/main/MIGRATION_GUIDE.md#new-feature-account_parameter_catalog_write_path-and-object_parameter_parse_on_set-enabled-by-default) for details.

~> **Note** Forward compatibility: account parameters that the provider does not support yet can be set with `value_type` (e.g. `key = "SOME_NEW_PARAMETER"`, `value = "10"`, `value_type = "INTEGER"`). The supported parameters are listed in the `key` field description below, and `value_type` is ignored for them (a warning is logged, see the `value_type` description). It requires the `ACCOUNT_PARAMETER_CATALOG_WRITE_PATH` experiment (enabled by default), because the rules for the value follow its behavior. When a later provider version starts to support the parameter, it is sent through the typed path, and the configuration does not have to change. The transition does not need configuration changes only if `value_type` matches the type of the parameter in Snowflake. Some types are easy to confuse: for example, an identifier (like a network policy name) is also accepted by Snowflake as a `STRING`, but once the provider supports the parameter, it is sent as a quoted, case-sensitive identifier, which may show a plan difference or fail. Check the parameter type in the [Snowflake documentation](https://docs.snowflake.com/en/sql-reference/parameters) before choosing `value_type`. See the [migration guide](https://github.com/snowflakedb/terraform-provider-snowflake/blob/main/MIGRATION_GUIDE.md#new-feature-forward-compatible-parameters-in-snowflake_account_parameter) for details.

# snowflake_account_parameter (Resource)

Resource used to manage current account parameters. For more information, check [parameters documentation](https://docs.snowflake.com/en/sql-reference/parameters).

## Example Usage

```terraform
resource "snowflake_account_parameter" "p" {
  key   = "ALLOW_ID_TOKEN"
  value = "true"
}

resource "snowflake_account_parameter" "p2" {
  key   = "CLIENT_ENCRYPTION_KEY_SIZE"
  value = "256"
}
```
-> **Note** Instead of using fully_qualified_name, you can reference objects managed outside Terraform by constructing a correct ID, consult [identifiers guide](../guides/identifiers_rework_design_decisions#new-computed-fully-qualified-name-field-in-resources).

- `value` (String) Value of account parameter, as a string. Constraints are the same as those for the parameters in Snowflake documentation. The parameter values are validated in Snowflake.

### Optional

- `timeouts` (Block, Optional) (see [below for nested schema](#nestedblock--timeouts))
- `value_type` (String) Type of `value`, used only for parameters that the provider does not support yet (forward compatibility). Valid values are (case-insensitive): `STRING` | `IDENTIFIER` | `INTEGER` | `FLOAT` | `BOOLEAN`. `value` is rendered the same way as for the parameters that the provider supports: `STRING` (also use it for enum parameters) is sent as a single-quoted string, `IDENTIFIER` as a quoted identifier (it can be fully qualified, e.g. `DB.SCHEMA.NAME`), and the others as a number or a boolean. The field is required for a parameter that the provider does not support, and it is ignored for the supported parameters (they are listed in the `key` field description), so it can stay in the configuration when a later provider version starts to support the parameter. Changes of this field are ignored for the supported parameters, but setting it for a supported parameter logs a warning. The field works only with the ACCOUNT_PARAMETER_CATALOG_WRITE_PATH experiment (enabled by default). The transition does not need configuration changes only if `value_type` matches the type of the parameter in Snowflake. Some types are easy to confuse: for example, an identifier (like a network policy name) is also accepted by Snowflake as a `STRING`, but once the provider supports the parameter, it is sent as a quoted, case-sensitive identifier, which may show a plan difference or fail. Check the parameter type in the [Snowflake documentation](https://docs.snowflake.com/en/sql-reference/parameters) before choosing `value_type`.
